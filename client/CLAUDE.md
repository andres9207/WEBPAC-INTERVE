# CLAUDE.md (client/)

Guía específica del dashboard. Ver también el [CLAUDE.md raíz](../CLAUDE.md) para el resumen del repositorio completo.

## Comandos

```
yarn                # instalar dependencias
yarn dev            # iniciar servidor de desarrollo Vite (puerto 3000)
yarn build          # build de producción
yarn preview        # previsualizar el build de producción
yarn lint           # eslint sobre src/**/*.{js,jsx,ts,tsx}
yarn lint:fix       # eslint --fix
yarn prettier       # prettier --write sobre src
```

No hay un test runner configurado para el cliente.

## Configuración de entorno

`client/.env` (copiar desde `.env.template`) necesita `VITE_API_URL` (por defecto `http://localhost:4000/api`) y claves opcionales de Firebase/Captcha.

## Arquitectura: estructura del template Berry

- Alias de rutas: `jsconfig.json` define `baseUrl: "src"`, por lo que los imports son absolutos desde `src` sin prefijo (p. ej. `import MainLayout from 'layout/MainLayout'`, no rutas relativas).
- **Enrutamiento** (`src/routes/`): `MainRoutes.jsx` anida las páginas protegidas bajo `PrivateRoute` (redirige a `/pages/login` si no está autenticado, usando `useAuth()`) envueltas por `MainLayout`; `AuthenticationRoutes.jsx` contiene las páginas públicas de autenticación bajo `MinimalLayout`. Las páginas protegidas nuevas se agregan como hijos lazy (`Loadable(lazy(...))`) en `MainRoutes.jsx`, y se registran como página en `tbl_pages` (migración + `server/prisma/seed.js`): el sidebar se arma en runtime desde `GET /app/get_menu` (`layout/MainLayout/MenuList`), no desde `src/menu-items/*.js`, que hoy solo alimenta las migas (`ui-component/extended/Breadcrumbs.jsx`). Receta completa en `engineering/standards/CRUD_STANDARD.md`.
- **Autenticación** (`src/contexts/authContext.jsx`): sesión basada en dos cookies que fija el servidor, ambas httpOnly + `secure` (en producción) + `sameSite: "Strict"` y no legibles desde JS: `token` (access token JWT, 15 minutos) y `refresh_token` (7 días). Ver "Sesiones" en `server/CLAUDE.md`. Es **una sola sesión por usuario**: iniciar sesión en otro navegador o dispositivo cierra la anterior, y la próxima petición de esa pestaña recibe un 401 y la manda al login. La cookie `id` (no httpOnly) guarda solo un cache serializado del perfil ya autenticado, para hidratar la UI sin esperar al backend; nunca es la fuente de verdad de la sesión y **no se envía al backend** (antes viajaba en cada petición como encabezado `currenuserapp`, que el servidor nunca leyó). **Ninguna petición envía el autor ni la identidad del usuario de la sesión** (`useBy`, `updatedBy`, `docCreateBy`, `usuAct`, `userId`…): el backend los toma de la cookie de sesión. Solo se envía el id del registro objetivo (p. ej. el usuario que se edita). `AuthProvider` siempre llama a `verifyTokenAPI` al montar (no puede gatear esa llamada leyendo la cookie de sesión, porque es httpOnly), expone `login`/`logout`/`hasPermission(perId)`/`permissionsCatalog`. `hasPermission` no tiene ningún caso especial por `useId`: solo revisa el array `permissions` que trae la sesión — "superadmin" es simplemente el perfil al que el servidor le asigna todos los permisos existentes (ver `server/CLAUDE.md`, "Resolución de permisos efectivos"), así que su acceso total llega por los mismos datos que el de cualquier otro usuario.
- **Idempotencia al crear** (`src/utils/idempotency.js`, DEC-016): todo formulario que **crea** un registro genera una clave con `newIdempotencyKey()` al abrirse (p. ej. en `newUser`/`newProfile`) y la pasa a la función de la API, que la envía en el encabezado `Idempotency-Key`. Se reutiliza en cada intento de guardar ese formulario y se descarta al abrir otro. Al editar no se envía. Subir un archivo usa una clave por archivo. El backend rechaza la creación sin clave (400).
  - `permissionsCatalog` (qué `per_id` significa qué acción, ej. `permissionsCatalog.security.users.create`) se trae de `GET /security/permissions/get_catalog` al iniciar sesión/loguearse — ya **no** existe `contexts/permissions/permissionsConfig.js` como constante local; el servidor (`common/constants/permissions.constants.js`) es la única fuente de verdad. `verifySession`/`login` esperan (`await`) a que cargue antes de bajar `initializing`, precisamente para que ninguna pantalla renderice con el catálogo a medias. Al leerlo, nunca pasar el valor crudo a `hasPermission` sin antes chequear que no sea `null`/`undefined` (`hasPermission(undefined)` es `true` a propósito, ver más abajo) — usar un helper tipo `canDo = (perId) => perId != null && hasPermission(perId)` como en `UsersPage.jsx`/`ProfilePage.jsx`.
- **Capa de API** (`src/api/`): `api/services/httpCliente.js` es una única instancia de axios (base `VITE_API_URL`, `withCredentials: true`) que deja que el navegador maneje la cookie `token` automáticamente; el interceptor de request solo adjunta el cache `id` en el header `currenuserapp`. El interceptor de response trata varios códigos de forma explícita. Ante un 401, primero intenta **renovar la sesión** una vez (`refreshSession()` → `POST /auth/refresh`, con una sola renovación en vuelo aunque fallen varias peticiones a la vez) y reintenta la petición original; esto aplica también a `verifyTokenAPI`, así que volver a la app después de 15 minutos no obliga a iniciar sesión. Si la renovación falla, limpia la cookie `id` y redirige a `/pages/login` (salvo que la petición pase `skipAuthRedirect: true`, usado por `verifyTokenAPI`). Los 401 de login, refresh y logout nunca disparan una renovación. `SocketProvider.jsx` reutiliza `refreshSession()` cuando el servidor rechaza el handshake por token vencido. 403 (falta de permiso, ya autenticado) **no** redirige ni limpia sesión, solo deja pasar el error; 409 (conflicto/duplicado) se propaga con `error.response.data` intacto para que el llamador lo muestre; 503 (BD caída/sin conexiones) se reintenta automáticamente una vez con el mismo `config` antes de rendirse. Ver "Manejo de códigos de error en el cliente HTTP" en `engineering/anti-patterns/SECURITY.md`. Cada dominio tiene un archivo `api/requests/<dominio>API.js` construido sobre `genericRequest` (`get`/`post`/`put`/`delete`) — sigue este patrón (no llamadas axios directas) al agregar nuevos endpoints.
- **Tiempo real**: `src/socket/SocketProvider.jsx` envuelve una conexión socket.io-client; el servidor une los sockets a una sala `user:<userId>` (`server/socket.js`) para emitir de forma dirigida (usado por `app/notifications`).
- **Mensajes de error al usuario, en dos capas**:
  - **Errores esperados de negocio/API** (falla un `save`/`delete`, 403 sin permiso, 409 duplicado, etc.): cada pantalla atrapa su propio `catch` y llama a `showError(err.response?.data?.message || 'mensaje de respaldo')` de `services/ToastService.js` (wrapper sobre `react-toastify`; el `<ToastContainer />` vive una sola vez en `App.jsx`). Es el patrón ya establecido en `UserDialog.jsx`/`ProfileDialog.jsx`/`ChangePassword.jsx`/etc. — al agregar un `catch` nuevo, usar `showError`, nunca solo `console.error` (eso deja al usuario sin ningún feedback visible). El interceptor de `httpCliente.js` (ver más arriba) no dispara toasts por su cuenta para no duplicar el mensaje que cada pantalla ya muestra.
  - **Excepciones no clasificadas durante el render de una ruta, o un 404 real de React Router** (ninguna ruta definida matchea la URL): `src/routes/ErrorBoundary.jsx`, montado como `errorElement` en `MainRoutes.jsx` y `AuthenticationRoutes.jsx` (React Router 7, `createBrowserRouter`/`RouterProvider`). Nunca expone el mensaje/stack real de un error inesperado en producción — mismo criterio que `error.middleware.js` del servidor (ver engineering/anti-patterns/SECURITY.md) — y detecta el caso de "deploy nuevo, pestaña vieja" (`Failed to fetch dynamically imported module` tras un cambio de hash de chunk de Vite) para recargar la página automáticamente en vez de mostrar un error confuso.
  - **Estas dos capas no se mezclan**: esta app no define ningún `loader`/`action` de React Router, así que `useRouteError()`/`isRouteErrorResponse()` **nunca** ven un error de la API — una promesa de axios que rechaza dentro de un componente se resuelve en su propio `try/catch`, nunca escala hasta el `errorElement`. Por eso `ErrorBoundary.jsx` no debe agregar casos por código HTTP (401/403/503, etc.) pensando que ahí es donde se le muestra al usuario el mensaje real del servidor — esa ruta es siempre la del `showError` de arriba. El único status de `isRouteErrorResponse` que sí es real y alcanzable en esta app es el 404 (ruta no encontrada).
- El theming, el chrome del layout (`Header`, `Sidebar`, `MenuList`) y los átomos de UI genéricos viven bajo `src/themes/` y `src/ui-component/`, siguiendo el layout estándar del template Berry — preferir reutilizar estos antes que introducir nuevos primitivos de UI.

## Estilo de código

- Configuración de Prettier: comillas simples, sin comas finales, indentación de 2 espacios, `printWidth: 140`, saltos de línea LF.
- ESLint: configuración flat en `eslint.config.mjs`, extendiendo los sets recomendados de React/Prettier — ejecuta `yarn lint` antes de dar por terminados los cambios del cliente.
